# gosched-bench

Стенд для двух статей:
- статья 1 — характеризация хвостовой задержки штатного планировщика Go
  (легковесные потоки) при смешанной нагрузке LC + BE в одном процессе;
- статья 2 — методика измерения и сравнения хвостовой задержки
  (открытый и закрытый цикл нагрузки, ширина интервалов от числа прогонов).

Постановка, факторы и гипотезы H1–H5 описаны в рабочем черновике статьи.

## Состав

```
cmd/server      тестируемый сервис: LC по TCP (или inproc), BE-генератор, метрики рантайма
cmd/loadgen     генератор LC-нагрузки: открытый цикл (по умолчанию) или закрытый (-mode closed)
cmd/calib       калибровка CPU-цикла и проверка его точности на машине
internal/       proto (кадры), spin (CPU-работа), dist (распределения), hist (гистограмма), rtm (runtime/metrics, cgroup)
sim/mgk.py      имитация эталонов M/G/k: fcfs, rr (квант 10 мс), prio (вытесняющий приоритет LC)
run/            make_plan.py (планы обеих статей), run.py (прогон плана), overhead.py
                (поправка ρ на накладные), env_check.sh, smoke.sh
analysis/       collect.py: results.csv (прогоны) и points.csv (точки, CI, эталоны, D, slowdown);
                article2*.py, h1trace.py: расчёты для статьи 2 и разбор трасс; figures.py: рисунки
deploy/         setup.sh (подготовка машины), run_all.sh (все серии подряд),
                push.sh / pull.sh (с ноутбука: залить код, забрать результаты)
```

Внешних зависимостей у стенда нет: только стандартные библиотеки Go и Python 3.
Для построения рисунков (`analysis/figures.py`) нужен matplotlib.

## Требования

- Go: `go.mod` фиксирует `toolchain go1.27.3`; более старый Go сам скачает нужный.
- Python 3.10+ (только стандартная библиотека).
- Для измерений в статью: Linux с cgroup v2, губернатор `performance`, без turbo.
  macOS подходит только для отладки (нет cgroup, taskset и контроля частоты).

## Запуск на арендованной машине (c7g.metal)

Всё делается с ноутбука, из корня репозитория. `HOST` — публичный адрес машины
из консоли EC2, ключ — `~/.ssh/gosched-bench.pem` (`chmod 400`).

```bash
bash deploy/push.sh $HOST                                   # 1. залить код (~1 с)
ssh -i ~/.ssh/gosched-bench.pem ubuntu@$HOST
cd gosched-bench && bash deploy/setup.sh                    # 2. пакеты, Go, службы, прерывания (~3 мин)
tmux new -s bench 'mkdir -p results && bash deploy/run_all.sh 2>&1 | tee -a results/run_all.log'   # 3. все серии (~17 ч)
# Ctrl-b d — отключиться; серия идёт дальше. Вернуться: tmux attach -t bench
bash deploy/pull.sh $HOST                                   # 4. с ноутбука: забрать результаты в results-aws/
```

Порядок фаз в `run_all.sh` и примерное время на c7g.metal:

| Фаза | Что делает | Прогонов | Время |
|---|---|---|---|
| env | сборка, снимок окружения в `results/env.txt` | — | 1 мин |
| calib | точность spin-цикла, разброс < 3% (иначе стоп) | — | 10 с |
| overhead | CPU на LC-запрос сверх E[S] → поправка ρ | 8 | 5 мин |
| ablation | статья 1: H1–H5 | 160 | 1,6 ч |
| co | статья 2: открытый vs закрытый цикл, сырые задержки | 60 | 0,6 ч |
| ci | статья 2: две конфигурации × 50 прогонов, сырые задержки | 100 | 1 ч |
| main | статья 1: полный план + точки «только LC» | 1320 | 13,6 ч |
| pack | архив `results-*.tar.gz` | — | 1 мин |

Любую фазу можно перезапустить: готовые прогоны пропускаются. Только часть:
`PHASES="co ci" bash deploy/run_all.sh`. Проверка самого скрипта за пару минут:
`WARMUP=1 DUR=3 LIMIT=1 bash deploy/run_all.sh` (в отдельный `OUT=/tmp/x`).

Раскладка ядер по умолчанию: 0–3 — ОС и прерывания, 4–19 — сервер
(`GOMAXPROCS = P`), 32–47 — генератор. Меняется через `SERVER_CPUS`,
`LOADGEN_CPUS`. `isolcpus` не используется: на изолированных ядрах Linux не
балансирует потоки, и все потоки сервера оказались бы на одном ядре.

Поправка ρ. Фаза overhead меряет CPU сервера на один LC-запрос без BE и
передаёт run.py `--lc-overhead-us`: λ_LC = (1−β)ρP / (E[S] + o). В пилоте без
поправки номинальные 0,3 / 0,7 / 0,85 давали фактическую загрузку
0,42 / 0,87 / 1,0; с поправкой ρ = 0,5 дала 0,49. Фактическая загрузка каждого
прогона пишется в `util_meas`.

Машину между сессиями останавливать (Stop): EC2 не тарифицируется, платится
только диск. SSH открыт только с IP, указанного при запуске; если IP сменился,
поправьте правило в security group.

## Быстрая проверка

```bash
go test ./internal/...
python3 sim/mgk.py --selftest     # сверка имитации с M/M/1, M/D/1, приоритетом
bash run/smoke.sh                 # сервер + генератор на одной машине, ~10 с
```

Smoke-прогон на одной машине почти всегда помечается `valid=false`: генератор
делит CPU с сервером и отстаёт от расписания. Это ожидаемо.

## Серия экспериментов

```bash
bash run/env_check.sh                       # окружение; код 1, если не годится
go run ./cmd/calib                          # разброс калибровки должен быть < 3%

python3 run/make_plan.py --pilot > plan-pilot.csv
python3 run/run.py --plan plan-pilot.csv --out results/pilot \
    --server-cpus 0-3 --loadgen-cpus 4-7 --warmup 5 --dur 30

python3 analysis/collect.py results/pilot --sim
```

Генератор на второй машине: `--loadgen-prefix 'ssh loadgen-host' --target <ip>:7070 --listen :7070`
(на той машине должен лежать собранный `bin/loadgen` по тому же пути).

`run.py` перемешивает порядок прогонов и пропускает уже выполненные, поэтому
прерванную серию можно запустить ещё раз той же командой.

## Факторы и абляции

| Фактор / гипотеза | Где задаётся |
|---|---|
| ρ, β, q, P | столбцы `rho, beta, q, P` в plan.csv |
| S_LC | `lc_dist`: `exp:50us`, `const:50us`, `bimodal:10us,1ms,0.05` |
| H1: очередь P | `be_yield` (например `1ms`): `runtime.Gosched()` внутри BE |
| H2: квант 10 мс | свип `q` через 10 мс |
| H3: опрос сети | `lc_source=inproc`: LC порождаются внутри процесса, без netpoller |
| H4: GC | `alloc_lc`, `alloc_be` (байт мусора), `gogc` |
| H5: троттлинг | `cpu_limit` (ядра, через `systemd-run -p CPUQuota`) |

## Закрытый цикл (статья 2: coordinated omission)

`loadgen -mode closed` работает как wrk: каждое из `-conns` соединений шлёт
следующий запрос только после ответа на предыдущий, по тому же пуассоновскому
расписанию и с теми же временами обслуживания, что открытый режим при том же
`-seed`. Если ответ опоздал, следующий запрос уходит сразу, но позже плана.

В `summary.json` закрытого прогона две задержки:

- `latency` — от фактической отправки (так считают закрытые генераторы);
- `latency_intended` — от запланированного момента (поправка на coordinated
  omission; гистограмма в `latency_intended_hist.json`).

`send_lag` в закрытом режиме — величина самого эффекта, на `valid` не влияет.

```
python3 run/make_plan.py --co > plan-co.csv    # 3 уровня ρ × 10 повторов × {open, closed}
python3 run/run.py --plan plan-co.csv --out results/co --server-cpus 0-3 --loadgen-cpus 4-7
python3 analysis/collect.py results/co         # столбцы lg_mode, int_p99_ns, achieved_rate
```

Столбец `lg_mode` в плане необязателен: если его нет или он пуст, прогон идёт
в открытом цикле, а `run_id` совпадает с прежним (старые серии не пересчитываются).

Проверка в контейнере разработки (ρ = 0,3, β = 0,5, q = 20 мс): закрытый цикл показал P99 ≈ 9 мс,
открытый — ≈ 113 мс при той же достигнутой интенсивности. Это и есть занижение,
которое демонстрирует статья 2. Открытый прогон там формально невалиден из-за шума контейнера; числа в статью не идут.

## Что пишется в results/<run_id>/

- `meta.json`: факторы, производные интенсивности, команды, окружение, коммит, статус.
- `server/final.json`: итог окна измерения (между SIGUSR1 и SIGTERM):
  гистограмма `/sched/latencies` (приращение), паузы GC, mark assist, getrusage,
  троттлинг cgroup, достигнутая BE-утилизация, задержка запуска обработчика.
- `server/metrics.csv`: те же метрики по секундам.
- `loadgen/summary.json`: перцентили R (от запланированного момента отправки),
  отставание генератора, серверные компоненты, флаг `valid`.
- `loadgen/latency_hist.json`: гистограмма R (ненулевые корзины, погрешность < 1%).
- `loadgen/samples.csv`: 1% запросов построчно с клиентскими и серверными метками.

Клиентские и серверные метки времени берутся с разных часов: сравнивать можно
только разности внутри одной стороны.

## Известные ограничения

- `/cpu/classes/*` в runtime/metrics обновляются только на циклах GC, поэтому
  CPU процесса считается через getrusage.
- `W_net` пока оценивается абляцией `inproc`. Прямое измерение через метки ядра
  (`SO_TIMESTAMPNS`) запланировано отдельным шагом.
- Индекс D может быть больше 1: штатный планировщик хуже FCFS-эталона
  (например, из-за отложенного опроса сети или шума стенда). Поэтому в
  points.csv есть и эмпирические показатели: `slowdown` = P99 / P99 точки
  «только LC» (β = 0, ρ' = ρ(1−β)) и `D_emp` с этим идеалом.
- В ВМ на Mac spin на 50 мкс растягивается в 2 раза (на x86 и, ожидаемо, на
  bare metal — нет). Фаза calib это показывает; поправка ρ всё равно берётся
  из измеренного CPU.
- BE-генератор сам живёт в рантайме: при полностью занятых P он может отставать,
  поэтому в итог пишется достигнутая, а не заданная BE-утилизация.
